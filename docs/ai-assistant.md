# AI-помощник Sentinel

В карточке инцидента доступны анализ и черновик postmortem (UI: `src/app/features/incidents/analysis/`). Запуск ручной: кнопка «Проанализировать». AI не изменяет инциденты, не запускает runbook, не отправляет уведомления и не выполняет команды. Viewer читает сохранённые результаты; operator/admin могут запрашивать анализ.

Текущая версия промпта: `incident-v6` (`server/ai/config.ts`). Смена версии инвалидирует кеш reusable jobs с прежним `prompt_version`.

## Что получает оператор

- Сводка и факты со ссылками на сохранённые источники.
- До четырёх гипотез, ограничения каждой и способы проверки.
- Следующие диагностические проверки и недостающие данные.
- Черновик postmortem: влияние, хронология, неопределённость причины, выполненные действия и предложения. Его можно скачать в Markdown с источниками.
- Отметка устаревшего анализа при изменении incident version, связанных событий, наблюдений сервиса, правил или зависимостей.
- Поле `statuses` (rootCause / missingData) обогащается **только сервером** после валидации; модель его не задаёт.

Ссылки проверяются сервером на принадлежность к переданному контексту. Выдуманное утверждение со ссылкой на существующий источник проходит эту проверку. Structured Outputs задают форму ответа и [не гарантируют истинность содержания](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes). Mock-тесты и `ai:smoke` не измеряют качество модели и не проверяют устойчивость к prompt injection. Оператор проверяет черновик. Нет логов приложения, истории деплоев и бизнес-метрик. Исторические правила не восстанавливаются: текущие правила помечены как текущие.

## Пост-валидация ответа

После Structured Outputs `validateAnalysis` (`server/ai/validate.ts`) отклоняет анализ без второго платного вызова, если нарушены измеренные ограничения:

| Слой             | Файл                           | Роль                                                                                                                                                                                                                                                                                                              |
| ---------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Числа ↔ метрики  | `claim-numbers.ts`             | Число привязывается к latency / error_rate (и синонимам: «задержка», «частота…», `error rate` / `error-rate` / `errorRate`). Pending метрик через мягкие разделители (`и`/`или`/`,`/`/`…); граница предложения (`.!;?…` и NFKC fullwidth) сбрасывает pending. Словесные числительные (`сто`, `оба`…) отклоняются. |
| Единицы          | `claim-units.ts` + `guards.ts` | После числа допускается семейство ms/мс (или единица, явно есть в корпусе). Чужие единицы (`s`, `ч`, `/h`, …) и ms у чистого `error_rate` без latency-источника — отказ.                                                                                                                                          |
| Лексика / токены | `guards.ts`                    | `guardText` (users/SLA/baseline/рост/порог), `assertGroundedTokens`, разбор чисел (`numsOf`, role fields вроде threshold).                                                                                                                                                                                        |

**Facts / summary / impact / timeline / actionsTaken / гипотезы (кроме verification):** числа + `guardText` + grounded tokens.

**Advice by design** (только числа + `guardText`, без token grounding): `prevention`, `nextChecks`, `hypotheses.verification`.

Кратко по контракту (как и раньше): summary/facts/impact/timeline/hypotheses/nextChecks/actionsTaken/prevention и оценочный rootCause обязаны ссылаться хотя бы на event, rule или dependency — одного limitations недостаточно. Оценочные слова (users/SLA/baseline) подтверждает только корпус observation. rootCause с измерением не может утверждать причину как подтверждённую; без измерения — только meta о неподтверждённости/нехватке данных, без чисел. В missingData нельзя утверждать воздействие/ущерб; числа только из текста limitations. Ссылка на source id ≠ семантическая верность факта (lexical ≠ semantic).

Unit-покрытие числовых кейсов: `tests/unit/ai-numbers.test.ts`. Docs-probes ревью, если появляются, живут вне CI.

## Настройка

`.env` исключён из Git и Docker build context. Ключ хранится только на сервере/worker, не в VITE-переменных и не в браузере.

```dotenv
AI_ENABLED=true
OPENAI_API_KEY=<ключ в локальном env-файле>
AI_MODEL=gpt-4.1-mini-2025-04-14
AI_DAILY_REQUEST_LIMIT=50
```

`docker compose up -d --build --wait sentinel worker` читает `.env`: API получает настройки AI без ключа, worker получает ключ. В dev `npm run dev` загружает `.env`, embedded worker использует тот же процесс. Без PostgreSQL (`npm run infra:up`) API не стартует — автоматического fallback на SQLite нет.

HA с AI: после подготовки TLS и HA-секретов используйте `docker compose --env-file .env --env-file .secrets/ha.env -f compose.ha.yaml up -d --build --wait`. В HA ключ передаётся только worker-a/worker-b, лимиты считаются отдельно по tenant-схемам. Обычный `npm run ha:up` с одним HA env-файлом не включает AI автоматически.

OpenAI Responses API используется с `store:false`, Structured Outputs и общей Zod-схемой. Отсутствие response storage не означает zero data retention провайдера. Справка: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [данные API](https://developers.openai.com/api/docs/guides/your-data).

До отправки ограничивается объём контекста: инцидент, измеренные события, свежие записи timeline, правила и зависимости. У категорий отдельные квоты внутри общего бюджета около 24 тысяч символов. Если записи не помещаются или обрезаются, это указано в ограничениях анализа. Идентификаторы источников непрозрачные. Известные формы API-ключей, Bearer-токенов и JSON/текстовые password, token, secret маскируются. Это не универсальный DLP. UI сообщает об отправке выборки в OpenAI до запуска.

## Надёжность и стоимость

`ai_analyses` одновременно хранит snapshot контекста, результат, аудитируемую идентичность запроса и durable outbox. POST фиксирует задачу в PostgreSQL, dispatcher публикует ID в отдельную quorum queue `<namespace>.ai.analysis.v1`. Consumer использует отдельный AMQP channel и prefetch=1; ожидание модели не занимает consumer мониторинговых событий.

- Повторный запрос одинакового контекста/model/prompt `incident-v6` переиспользует queued/running/succeeded job, пока контекст не снят хранением. Совпадение защищено partial unique index и tenant-scoped advisory lock. Результат предыдущей схемы/промпта помечается как несовместимый: старый текст не переписывается.
- Не более одной активной задачи на инцидент. После успешного переиспользуемого анализа следующий запрос, даже с новым контекстом, доступен через минуту. Неудачный анализ — тоже через минуту. Результат с удалёнными источниками или прежней схемой этот интервал не занимает.
- До 50 новых задач на tenant за скользящие 24 часа по умолчанию (`AI_DAILY_REQUEST_LIMIT`). Это лимит запросов, не жёсткий долларовый budget.
- Максимум два обращения к модели на задачу, 45 секунд на обращение, общий deadline задачи 5 минут; SDK automatic retries отключены. Только временные ошибки допускают повтор через 30 секунд.
- Lease 90 секунд и fencing token запрещают старому worker перезаписать результат после восстановления задачи. Exactly-once inference не обещается.
- Публикация подтверждается брокером; pending/потерянные broker wakeups повторно публикуются из БД. Истёкшие задачи переходят в failed при работе dispatcher.
- Сохраняются input/output tokens, длительность и оценка стоимости успешного ответа. Для `gpt-4.1-mini-2025-04-14` оценка $0.40/$1.60 за миллион input/output tokens, cached discount не учитывается. Для произвольной модели стоимость null. Тарифы: [страница модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

Отказ валидации, неизвестные source ID и невалидный JSON не сохраняются как успешный анализ. Ошибки доступа/billing возвращают оператору понятное сообщение без сырого ответа провайдера или ключа. Отключение AI не блокирует incident ingestion.

Login-аудит пишется только после успешной записи session allowlist в Redis; сбой Redis rate-limit не валит auth/health (fail-open), но login/anon/authn fail-closed (503). После потолка authn неизвестные токены получают не более 5 PG fallback-проверок в минуту (`authn-fallback`).

Общая retention затирает context завершённых анализов старше срока и снимает `context_retained`: список sources становится пустым, в limitations остаётся пометка об удалении, а результат исключается из кеша. Текст результата сохраняется. Ссылка на источник, которого больше нет в context, показывается как «удалён». Новой векторной БД, агента с инструментами или микросервиса не добавлено.

## Проверки

`npm test` проверяет схему, источники, маскирование, строгий Responses request, refusal, ошибки провайдера и числовую/единичную пост-валидацию (`ai-numbers`).

`npm run test:integration` использует реальные PostgreSQL/RabbitMQ и тестовую модель без внешних запросов: очередь, дедупликация, cache, staleness, восстановление lease, fencing, deadline, бюджет, tenant-контекст и RBAC/CSRF.

`npm run test:e2e` проверяет панель, источники, отображение недоверенного текста без исполнения, скачивание черновика и мобильный размер; ответ AI подставляется на границе HTTP. Это тест интерфейса, а не качества модели.

`npm run ai:smoke` делает один платный запрос с синтетическим инцидентом. Он не входит в автоматические тесты и выводит только безопасную статистику.
